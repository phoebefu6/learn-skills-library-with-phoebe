Learn Your Own Skills Library with Phoebe · Session 3 of 6

One job, clear inputs, a built-in check

The description decides whether a skill fires. The body decides what happens next. A good body reads like a short procedure a sharp new colleague could follow: what this is for, what to ask for first, the steps, the shape of the answer, and a check before anything goes back. Tonight we write that body, and move everything else out of the main file until a step needs it.

Part 1 · covers one job per skill and the body's sections

One job, five sections

5 min live

A skill body that works tends to have the same five parts, whoever wrote it: a purpose, the inputs to ask for, numbered steps, an output format, and a self-check before returning. None of the vendors mandates these headings; the specification only requires the frontmatter. But each part answers a question the assistant would otherwise guess at, and every guess is a place where two runs of the same skill come out different.

LiveFive sections3 min▶
SectionThe question it answersThe Anthropic pattern behind it
PurposeWhat this is for, in two sentences, and what it is not forConcise context; the assistant is already smart
Inputs to ask forWhat must be in hand before step 1, and what to do if it is notWorkflows with clear steps
StepsThe order of work, numberedWorkflows with checklists the assistant can copy and tick

Self-checkWhat must be true before it returnsFeedback loops: validate, fix, repeat

Anthropic's authoring guide also describes an examples pattern: show one input and the output you want, because a single concrete pair often teaches the style faster than a paragraph of adjectives. Keep one short example in the body if it earns its lines; keep a gallery of full examples in a reference file (Part 3).

LiveOne job2 min▶

A skill that does two jobs needs a description that names both, and that description now shares words with both jobs' neighbours. OpenAI's Codex guide states the norm directly: keep each skill focused on one job. The reason is routing, not tidiness.

The session 4 bench shows the direction. Its constructed library starts with one combined skill, notes-and-interviews, which writes meeting minutes and synthesises research interviews. Splitting it into meeting-minutes and interview-synthesis took right outcomes from 54 to 55 of 60 requests, and request 15, "who agreed to do what on yesterday's call?", found its skill for the first time. The bench router is a modelled stand-in, a BM25 keyword scorer, not the language model a real assistant uses: read it for the direction, not the size.

A quick test for two jobs: if the output format section needs an "if it is X, return this; if it is Y, return that" switch, you have two skills sharing a folder.

Self-studyDegrees of freedom3 min▶

Anthropic's guide asks how much freedom each step should leave the assistant. High freedom: plain-language guidance, for work where many approaches are fine and judgment carries it (framing a client's objectives). Medium: a preferred pattern or pseudocode with some parameters (the section order of a brief). Low: an exact script or command, for steps where one slip breaks something (a fixed file name, a check that must run).

The guide's picture, paraphrased: on a narrow bridge with a drop on both sides, give exact guardrails; in an open field with no hazards, give a direction and let the assistant find the path. Most skills mix both. Pemberton & Thistle's brief (constructed) leaves the analysis open and locks down the sections and the check.

Real world

Validate, fix, repeat. Anthropic's skill authoring best practices describe feedback loops as one of the patterns that most improves output: run a validator, fix what it reports, and run it again until it passes. The pattern is old (it is how a compiler and a test suite work); what is new is writing the loop into the skill itself, so the assistant runs it every time instead of only when someone remembers to ask.

Part 2 · covers inputs to ask for and the built-in check

Ask first, check before returning

5 min live

The two gates in the body are where most skills are weakest. Without an inputs section, the assistant fills a missing client name or deadline with something plausible, and a plausible invention in a client brief is worse than a question. Without a self-check, the only test of the output is the person who reads it, often the client. Both gates are a few lines each.

LiveInputs: ask, do not guess2 min▶

List every input the steps depend on, and say what to do when one is missing. Most skills need three kinds:

  • Material: the intake notes, the transcript, the data file.
  • Facts the material may not carry: the client's name, the deadline, the budget band.
  • Choices only the requester can make: two pages or one, internal or client-facing.

Then one rule per input: ask, use a stated default, or stop. "If the deadline is not in the notes, ask; do not estimate one" is a line that prevents a whole class of confident errors. Defaults are fine when they are written down and visible in the output ("Length: two pages, the default").

LiveA self-check the assistant can run3 min▶

A self-check is a short checklist the assistant works through before returning. Anthropic's guide suggests writing it as a list the assistant can copy into its answer and tick, so progress is visible. Each item must be verifiable: "all five sections present" can be checked; "the brief is high quality" cannot.

Where a check is deterministic, move it into a script. Anthropic's overview notes that when a skill runs a script, the script's code does not enter the context, only its output does. A 40-line checker costs one line of context per run. For high-stakes work the guide goes one step further: have the assistant write a plan to a file, validate the plan with a script, and only then execute it. Plan, validate, execute.

★ A self-check section (constructed Pemberton & Thistle example)## Before you return Copy this list into your answer and tick each item: - [ ] Ran scripts/check_brief.py on the draft and it printed OK - [ ] Every objective is one the client stated in the notes - [ ] Every open question names who must answer it - [ ] No fee, rate or price appears anywhere If any item fails, fix that section and run the check again.
Self-studyExplain the why2 min▶

The open format's authoring guidance favours instructions that carry their reason over rigid ALWAYS and NEVER rules: an assistant that knows why fees stay out of a brief ("pricing is agreed separately, and a number in the brief becomes a commitment") handles the edge case the rule never named. Anthropic's guide makes the matching point about length: be concise and assume the model is already smart, because "the context window is a public good". Every sentence in the body competes with the conversation, the other skills' descriptions and the work itself.

Together these suggest a simple edit test: for each line, would a capable colleague get this wrong without it? If not, cut it. If yes, keep it and add the reason.

Real world

Scripts that solve, not scripts that shrug. Anthropic's best practices ask skill authors to make bundled scripts handle their own errors rather than defer the problem back to the assistant, and to explain every constant in them instead of leaving unexplained magic numbers (the guide's phrase is "voodoo constants"). A check script that prints a clear "missing: open questions" is something the assistant can act on; a stack trace is something it has to guess about.

Part 3 · covers references and scripts kept out of the main file

Load it only when a step needs it

5 min live

Everything in SKILL.md loads the moment the skill fires. Everything in a separate file loads only when a step reads it. That difference, Level 2 against Level 3 in session 1's picture, is the reason to split. House style rules, a gallery of example outputs and lookup tables are all things some runs need and most do not.

LiveUnder 500 lines, references one level deep3 min▶

The open specification and Anthropic's authoring guide agree on the limits:

  • Keep the main SKILL.md under 500 lines. The spec recommends the body stay under 5,000 tokens.
  • Reference files one level deep from SKILL.md. SKILL.md points to references/house-style.md; that file does not point on to a third. A chain of references is one the assistant may only partly read.
  • A table of contents for any reference file over 100 lines, so a partial read still shows what the file holds.
  • Descriptive file names (brief-examples.md, not doc2.md), and forward slashes in paths, which work on every system.

The pointer in the body says when to read the file, not only that it exists: "Before step 4, read references/house-style.md" loads it at the step that needs it.

LiveSkills, project instructions and prompt craft2 min▶

Not everything belongs in a skill. Project instructions load every time, for every request in that project: the open AGENTS.md format is a plain Markdown "README for agents", stewarded by the Agentic AI Foundation under the Linux Foundation, where the nearest file in the directory tree takes precedence and an explicit prompt from you overrides it. A skill loads only when a request matches. So: a rule that applies to everything in a repository goes in project instructions; a procedure for one kind of task goes in a skill. One product's take on the pair is in Learn Codex, session 3.

How to phrase an instruction well (roles, examples, structure) is prompt technique, and it has its own course: Learn Prompt Engineering. Turning one written SOP into one skill in Claude, step by step, is Learn Claude, session 3.

Self-studyAvoid time-sensitive text and keep terms consistent2 min▶

Time-sensitive text rots. "Until March, use the old template" is wrong the day after March and nobody edits it. Anthropic's guide suggests stating the current method plainly and, if the old way still matters, moving it under a clearly labelled old-patterns section, ideally in a reference file, so it does not compete with the current steps.

One term, everywhere. If step 2 says "brief", step 5 says "proposal" and the checklist says "document", the assistant has to decide whether these are three things. Pick one word for each thing and use it throughout the body, the reference files and the script's output.

Real world

Only the file the question needs. Anthropic's authoring guide illustrates the split with a data-analysis skill for BigQuery that keeps each business domain's table definitions in its own reference file, for finance, sales and so on. A question about sales reads the sales file; the other files stay on disk and cost no tokens. The same move works for any skill with domain-specific detail: one file per domain, one pointer per file.

Build-along

Split one bloated skill

★ 22 min · everyone builds

Pemberton & Thistle's client-brief skill (Constructed Pemberton & Thistle example) has grown to about 600 lines over a year of fixes. You will mark every block in it, keep the job in a lean SKILL.md, move the reference material out, delete the history, and specify a check script. Your own bloated skill will have different blocks in different proportions; the marking method is the point.

Open the skill as you found it. The frontmatter is the one session 2 wrote and the session 4 bench routes on. Below it, a year of additions. The excerpt shows the shape; the whole file runs to about 600 lines (constructed).

★ Step 1 · client-brief/SKILL.md as found (constructed excerpt, about 600 lines in all)--- name: client-brief description: Drafts a two-page client project brief from intake notes: objectives, scope, deliverables, timeline and open questions. Use when a new engagement starts and someone asks for a project brief, a scoping brief or a brief for the client. --- # Client brief We write briefs in British English. Headings in sentence case. Never use "leverage". Dates as 3 March 2026. Numbers under ten in words... [... 140 lines of house style rules ...] Read the intake notes and write the brief. Objectives first. Remember the Norbury Council brief where the timeline was missing!! Always add a timeline. [... steps, inputs and output rules scattered across 120 lines ...] ## Example 1: Halden Water (full brief) [... three complete example briefs, 260 lines ...] ## Notes In 2025 we tried a one-page version; the partners did not like it... [... 80 lines of history ...]

Mark every block with one of six labels. Go through the file top to bottom and tag each paragraph. Be strict: a block that is half step and half history gets split, not tagged twice.

★ Step 2 · the six labels and where each one goesJOB STEP -> SKILL.md, numbered steps INPUT -> SKILL.md, inputs to ask for OUTPUT FORMAT -> SKILL.md, the template CHECK -> SKILL.md checklist, or scripts/ if deterministic REFERENCE MATERIAL -> references/, one file per kind HISTORY -> delete (the reason may survive as one "why" clause)

Write the lean SKILL.md. Purpose, inputs, steps, output format, self-check and a pointer to each file, in that order. Here it is in full, 55 lines with the frontmatter. Notice that the history survived only as reasons ("a missing timeline was the most common complaint").

★ Step 3 · the new client-brief/SKILL.md, shown in full (constructed)--- name: client-brief description: Drafts a two-page client project brief from intake notes: objectives, scope, deliverables, timeline and open questions. Use when a new engagement starts and someone asks for a project brief, a scoping brief or a brief for the client. --- # Client brief ## Purpose Turn intake notes from a won engagement into a two-page brief the client can approve. This skill scopes work already agreed; it never prices it. ## Inputs to ask for - Intake notes. If missing, ask for them; do not draft from memory. - Client name. If the notes do not state it, ask. - Start date and deadline. If either is missing, ask; do not estimate. - Audience: client-facing (default) or internal. State which in the brief. ## Steps 1. Read the intake notes end to end before writing anything. 2. List the client's objectives in their own words, at most five. 3. Write scope as in-scope and out-of-scope lists. 4. Before writing, read references/house-style.md for spelling, dates and banned words. 5. Draft the brief in the output format below. 6. If unsure about tone, read references/brief-examples.md and match the closest example. Do not copy its content. 7. Run the self-check. Fix and re-run until it passes. ## Output format # Project brief: [client name] ## Objectives ## Scope ### In scope ### Out of scope ## Deliverables ## Timeline (one row per milestone: date, milestone, owner) ## Open questions (each question names who must answer it) ## Self-check before returning Copy this list into your answer and tick each item: - [ ] Ran scripts/check_brief.py on the draft; it printed OK - [ ] Every objective appears in the intake notes - [ ] Timeline present (a missing timeline was the most common client complaint) - [ ] Every open question names who must answer it - [ ] No fee, rate or price anywhere (pricing is agreed separately, and a number in a brief reads as a commitment) If any item fails, fix that section and run the check again. ## Files - references/house-style.md: spelling, dates, banned words (step 4) - references/brief-examples.md: three past briefs, for tone (step 6) - scripts/check_brief.py: section and timeline check (self-check)

Give the big reference file a table of contents. brief-examples.md is about 260 lines, well over 100, so it opens with a table of contents. A step that reads only the top of the file still learns what is in it.

★ Step 4 · references/brief-examples.md, the first lines (constructed)# Brief examples Three approved briefs, for tone and level of detail only. Do not reuse their content. ## Contents 1. Halden Water: network resilience review (client-facing, 2 pages) 2. Norbury Council: service redesign scoping (client-facing, 2 pages) 3. Fenwick: internal market-entry brief (internal, 1 page) ## 1. Halden Water: network resilience review ...

Write the check script's contract before its code. Say what it reads, what it checks and exactly what it prints, so the assistant knows how to act on every result. This is the specification for scripts/check_brief.py; we describe it here and have not run it, so no output below is a real result.

★ Step 5 · the contract for scripts/check_brief.py (constructed)READS the draft brief, as a Markdown file path CHECKS 1. all six headings present: Objectives, Scope, Deliverables, Timeline, Open questions, and the title line 2. Timeline has at least one dated row 3. every Open questions line names an owner ("- Who: ...") 4. no currency symbol or the words fee, rate, price PRINTS one line per failure, naming the section, e.g. missing: Open questions or the single word OK when every check passes EXIT 0 on OK, 1 on any failure NEVER edits the draft; fixing is the assistant's job (step 7)

Delete the history, keep the reasons. The 80 lines of "what went wrong last year" felt like institutional memory, but every run paid for them. What was worth keeping fit in two clauses on the checklist. If the story matters to people, put it in your team's notes; the assistant needs the rule and its reason, not the anecdote.

Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · A skill writes meeting minutes and also synthesises research interviews. What is the main reason to split it in two?

One job per skill is a routing rule. On the session 4 bench (a modelled stand-in, not a real assistant), splitting the combined skill took right outcomes from 54 to 55 and request 15 found its skill.

2 · The lean client-brief skill fires on a request. Which of its files are in the assistant's context right after it fires?

Level 2 is the body, loaded on firing. Level 3 is everything else, loaded on demand; a script's code never enters the context, only what it prints.

3 · Why write the self-check into the skill instead of reviewing the output yourself?

The self-check is a feedback loop inside the skill: validate, fix, repeat. It does not replace testing the skill itself, which is session 5.
