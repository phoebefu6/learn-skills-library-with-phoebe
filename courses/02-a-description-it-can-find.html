Part 1 · covers the description as the router's only evidence

The only thing the router reads

5 min live

When you send a request, the assistant does not open every skill to see which one fits. At that moment it holds, for each installed skill, a name and a description, nothing more. Anthropic's overview says the description is what Claude matches your request against when deciding whether to trigger a skill; the agentskills.io guide says it carries the entire burden of triggering. If the words a person would type are not in the description, the skill is invisible, however good its instructions are.

LiveWhat the router has, and what it lacks3 min▶

It has Level 1 from session 1: every installed skill's name and description, about 100 tokens each. Codex documents the same starting point: each skill's name, description and file path, with the full SKILL.md read only once a skill is selected. Claude Code loads descriptions in the session and the full content only when a skill is invoked.

It lacks everything else. It has not read your steps, your reference files or your examples. It cannot know that "Data analysis." means survey results, because nothing in those two words says so.

And it may not even have the whole description. Listings have a budget. Claude Code caps the listing at about 1% of the model's context window and truncates the combined description and when_to_use text at 1,536 characters; Codex caps its initial list at 2% of the window (8,000 characters when the window size is unknown) and shortens descriptions first when the library is large. The practical rule, in Codex's own advice: put the main use case and trigger words first, so the matching survives the shortening.

Real world

The vendors' first troubleshooting step. When a skill is not triggering, Claude Code's documentation starts with "Check the description includes keywords users would naturally say". Not "check the instructions", not "check the model": the description, because it is the only evidence the decision is made on. The figure above is that sentence, drawn with a keyword router standing in for a language model; a real assistant reads meaning as well as words, but it still reads only these words.

Part 2 · covers what + when and the trigger phrases people really type

What it does, and when to use it

5 min live

Every source agrees on the shape. The open specification defines the description as what the skill does and when to use it. Anthropic's best practices say a description must include both. Most first drafts carry only half: the "what" ("Drafts briefs") with no situation that should trigger it, or a vague situation ("Helps with documents") with no output at all. The second half is where the requests live.

LiveThe two halves2 min▶

What is a verb and an object, plus the parts of the output: "Drafts a two-page client project brief from intake notes: objectives, scope, deliverables, timeline and open questions." It tells the router, and you in six months, what comes out.

When is the situation and the asks: "Use when a new engagement starts and someone asks for a project brief, a scoping brief or a brief for the client." It is the half that matches requests, because requests describe situations ("we just won the job") far more often than they name outputs.

Anthropic's best practices contrast specific descriptions with vague ones such as "Helps with documents": true of half the library, so it helps the router choose nothing. On the bench, rewriting all eighteen vague one-liners into what + when took the constructed library from 14 to 52 of 60 requests routed right.

LiveTrigger phrases people really type3 min▶

Write down how colleagues actually ask, before you write the description. Real requests are casual ("can you nudge them politely"), name a file type rather than a task ("CSV attached"), and are often indirect: they describe the situation and never name the domain. The agentskills.io guide puts it as describing the user's intent, not the implementation: say what the person is trying to get done, not how the skill does it internally.

Two bench requests show both sides (constructed, rung 2, stand-in router):

The second one is fixed in session 4 by splitting a two-job skill, not by bolting the phrase on. Keep a list of real asks for each skill: it is the test set session 5 builds on.

Self-studyThird person or imperative? Contested2 min▶

The sources disagree on voice. Anthropic's best practices say "Always write in third person" (their example: "Processes Excel files and generates reports"). The agentskills.io guide says "Use imperative phrasing", as in "Use this skill when...".

Neither source measures the difference, and both agree on the part that matters: say what the skill does and when to use it. The bench descriptions mix the two, a third-person "what" and an imperative "Use when", which satisfies both readings. Pick one convention for your library and keep it consistent; do not expect either choice to rescue a description that lacks the "when".

Real world

Front-load, because the end may be cut. OpenAI's Codex guide asks for concise descriptions with clear scope and boundaries and tells authors to put the main use case and trigger words first, so matching still works when descriptions are shortened in a large library. A description that opens with "This is a helpful skill that can assist with..." spends its safest characters on nothing.

Part 3 · covers "do not use for" lines and naming schemes

Boundaries and names

5 min live

A good description attracts the right requests. In a library it also has to stop attracting a neighbour's. Two skills that share a domain, survey design and survey analysis in the Constructed Pemberton & Thistle example, share words too, and a word in both descriptions pulls requests both ways. A "Do not use for" line names the neighbour that owns those requests, and a consistent naming scheme makes the neighbours easy to see.

LiveDo not use for3 min▶

One line at the end: what this skill is not for, and which skill is. "Do not use for responses that came back, cross-tabs or charts (survey-analysis)." It does two jobs: it tells the router where the boundary is, and it tells the next person who edits the library that the neighbour exists.

On the bench (constructed, stand-in router), adding a not-for line to every description halved the false fires, requests that should reach no skill, from 6 to 3. It is not free: the library grew from 3,605 to 5,186 characters, and because every score moved, one new false fire and one new misroute appeared. Session 4 shows the whole trade.

Write the boundary in the neighbour's words, not your own. The stand-in counts every word after "Do not use for" as evidence against the skill, ignoring the neighbour's name in brackets. So a not-for line that repeats your own skill's words penalises your own requests. That happened while the bench was being built: an early survey-design line contained the word "survey", and pushed survey-design requests away from survey-design. A language model reads the negation rather than counting words, so a real assistant may forgive the slip; the habit costs nothing either way.

LiveA naming scheme2 min▶

The spec fixes the characters: 1 to 64, lowercase letters, numbers and single hyphens, matching the folder name. Anthropic adds no XML tags and no reserved words "anthropic" or "claude". Within those rules you choose a scheme.

PatternExampleNote
Gerund (Anthropic's suggestion)processing-pdfsReads as an activity
Noun phrase (Pemberton & Thistle's choice, constructed)client-brief, survey-analysisReads as the thing produced
Vague (avoid)helper, utils, toolsAnthropic names these as names to avoid

The scheme matters less than using one. When survey-design and survey-analysis share a prefix, anyone scanning the library sees the pair and checks their boundary; when one is called questionnaire-helper, nobody does.

Self-studyPushy or precise? Contested2 min▶

The agentskills.io guide tells authors to "Err on the side of being pushy": agents tend to under-use skills, so name more situations. The same guide, for a skill that fires when it should not, says "Add specificity about what the skill does not do". Anthropic's Claude Code docs answer over-triggering with "Make the description more specific", or with disable-model-invocation: true so only you can call it.

Both pressures are real, and they pull opposite ways. The bench shows both: not-for lines cut false fires, and session 4's keyword-stuff trap shows what pushiness done badly costs. A keyword router cannot say which one a real language model rewards more, and no source has measured it. Session 4 runs both traps; session 5 gives you the test set to decide for your own skills.

Real world

The open format's advice for false triggers. The agentskills.io guide on optimizing descriptions treats a skill that fires on the wrong requests as a description problem with a description fix: add what the skill does not do, then re-test on near-misses, the requests that look like yours but belong elsewhere. It also warns against the opposite reflex, copying words from failed requests into the description, because it fits the test set rather than the people.

Try requests the rewrite does not name. Type a way you would really ask for one of these four that avoids the description's words. "is anything in this deck made up?" is a fact-check, but on rung 2 the stand-in fires slide-polish at 1.60, because "deck" is a slide-polish word and citation-check (1.08) shares nothing distinctive with it. That is the gap a language model may close by meaning and a keyword router cannot; write the phrase down as a test case for session 5, not as a word to bolt on.

Rewrite from requests, not from the instructions. The fastest way to a good "when" half is to collect five real requests first and write the description so each of them shares at least two distinctive words with it. Writing it from the instruction body produces the vocabulary of the method ("BM25", "pivot", "cross-tabulation"), which is not how anyone asks.

Homework

Before session 3

30 min
  1. Write three descriptions for your own skills in the two-half shape: verb + object and output parts, then "Use when" with the situation and the phrases people type. Main use case and trigger words first.
  2. Collect ten requests people would really type across those three skills, from your chat history or by asking two colleagues how they would ask. Include at least two that never name the domain.
  3. Add "Do not use for" lines to one neighbouring pair. Name the neighbour in brackets and check that each line uses the neighbour's words, never its own skill's.
  4. Check every name against the spec: 1 to 64 characters, lowercase, numbers and single hyphens, matching the folder, no "helper" or "utils", and one scheme across the library.
Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · A skill has excellent step-by-step instructions but never fires. Where do you look first?

The body loads only after the skill is chosen. Claude Code's first troubleshooting step is to check the description includes the keywords users would naturally say.

2 · Which description gives the router the most to match?

C has the "what" but no "when". D has both halves: the output and the situations and phrases that should reach it, with the main use case first.

3 · Why should survey-design's "Do not use for" line avoid the word "survey"?

On the stand-in this is arithmetic; a language model reads the negation and may forgive it. Either way, the boundary is clearest written in the words only the neighbour's requests use.
