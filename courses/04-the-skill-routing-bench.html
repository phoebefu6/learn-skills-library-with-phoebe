Part 1 · covers what a router reads, and the stand-in

The router reads descriptions, nothing else

5 min live

Before a skill fires, the assistant has seen exactly one thing about it: its name and description. Anthropic's overview says the description "is what Claude matches your request against"; the open format's guide says it "carries the entire burden of triggering". Real assistants do that matching with a language model. The bench uses a simpler reader, so you can watch every score.

LiveWhat the stand-in is, and what it is not3 min▶

It is BM25, a keyword scorer from information retrieval (Robertson and Zaragoza, 2009). For each request it scores every description: words the two share count for more when they are rare across the library, repeated words add less and less, and long descriptions are scored down a little. The highest score fires if it reaches a firing line of 1.20; below that, no skill fires. Words after "Do not use for" count against the skill. Ties go to the skill listed first.

It is not how any assistant routes. Claude, Codex and Copilot pick a skill with a language model reading the same names and descriptions, and none of them publishes the method. A model understands "translate" and negation; BM25 only counts words. What the stand-in shares with them is the input and the pressures: vague text, two skills claiming one request, near-identical twins, and descriptions that grow. Read the bench's numbers as directions, never as a forecast for your assistant.

LiveTry one request yourself2 min▶

Type a request the way a colleague would and pick a rung. The router shows which skill fires and the three highest scores.

Self-studyThe scoring, written out3 min▶

For each word the request shares with a description: weight = idf x tf' / (k1 + tf'), where tf' = tf / ((1 - b) + b x length / average length). The review by Robertson and Zaragoza notes that experiments tend to favour k1 below 2 and b above 0.5; the bench uses k1 = 1.2 and b = 0.75. The idf is ln(1 + (N - n + 0.5) / (n + 0.5)), where N is the number of skills and n the number whose description contains the word, so a word in every description is worth almost nothing.

That last property matters in Part 3: adding a common word to every description does nothing for routing, while adding a neighbour's distinctive word does a lot of damage. A Python twin in the repository re-implements the router and must print the same numbers as the browser before any page quotes one.

Real world

Vendors say it the same way. Claude Code's troubleshooting for a skill that does not trigger starts with "Check the description includes keywords users would naturally say", and for one that triggers too often, "Make the description more specific". Codex's guide asks for descriptions with clear scope and boundaries, with the main use case and trigger words first. Whatever reads the description, it can only use the words you gave it.

Part 2 · covers the four outcomes and the ladder

Four outcomes, one ladder

5 min live

Accuracy alone hides how a library fails. A request can reach the right skill; reach the wrong skill (a misroute); reach no skill though one exists (a miss); or fire a skill when it should fire none (a false fire). Each points at a different fix, and the ladder below moves them differently.

LiveEach outcome points at a different fix3 min▶
OutcomeWhat happenedUsual fix
No skill firedNo description shared enough words with the requestSay when to use it, in the words people type (session 2)
Wrong skillA neighbour's description matched betterA "do not use for" line, or split a skill doing two jobs
Fired on a noneA description matched a request no skill should takeMake the description more specific; remove stray words
Right skillThe description carried the request homeKeep it that way: test after every edit (session 5)
LiveReading the ladder2 min▶

Rung 1 fails by silence: 42 of 60 requests fire no skill, because one-liners such as "Surveys." and "Research helper." share almost no words with what people type. Its only collision is telling: "Surveys." is the one description containing the word survey, so all three survey-analysis requests go to survey-design. Rung 2 fixes the silence and exposes the opposite failure: six requests that should fire nothing now fire something. Rung 3 halves those false fires. Rung 4 splits notes-and-interviews into meeting-minutes and interview-synthesis, and "who agreed to do what on yesterday's call?" finally reaches a skill.

Self-studyWhy one change moves rows you did not touch3 min▶

On rung 3, "what's the time in Singapore right now?" starts firing newsletter at 1.23. Nobody edited the newsletter's "Use when it is time to write" sentence. What changed is everything else: the "do not use for" lines made the library's descriptions longer on average, which shifts every length-normalised score a little, and "time" crossed the line. Real routers are not BM25, but the lesson transfers: any edit to a library is an edit to every request's odds, which is why session 5 re-runs the whole test set after each change.

Real world

The vendors' advice, in bench terms. Anthropic's authoring guide calls "Helps with documents" a description to avoid and asks for both what the skill does and when to use it: rung 1 against rung 2. The open format's guide adds that when a skill false-triggers, the description "may be too broad. Add specificity about what the skill does not do": rung 3.

Part 3 · covers keyword stuffing and near-duplicate skills

Two moves that make it worse

5 min live

Two moves look like progress and are not. Keyword stuffing ("also use for reports, decks, notes...") does make misses fall. A near-duplicate, a skill copied with a small edit, looks like harmless redundancy. The bench prints the bill for both.

LiveKeyword stuffing: the honest nuance3 min▶

Stuffing is not useless, and pretending it is would be a lie in the other direction. On the bench it does fix the one remaining miss: "can you fix the spelling and tone of this paragraph" reaches house-style once its description says "tone". The trouble is where the other new words came from. Each stuffed description borrowed its neighbours' trigger words, so onboarding-guide now claims workshops and survey-design claims "survey tool" questions that needed no skill. Net: 53 of 60, two below rung 4, and 1,509 more characters loaded in every session.

The open format's guide says to "err on the side of being pushy" and, in the same guide, warns against adding specific keywords from failed queries. Both are right: be generous about the situations your skill covers, never about your neighbours' vocabulary.

LiveNear-duplicates: why the copy wins2 min▶

sector-scan is market-scan with one sentence edited to "how big a sector is, for a sector scan, a market map". Two things follow. Every word the twins share is now in two descriptions, so it counts for less in both. And the edited sentence happens to match "how big is the market", so the copy outscores its original, 4.37 to 3.28. The bench names the pair because that is what an overlap audit needs: not "accuracy fell" but "these two are fighting".

Codex's docs note that skills with the same name are not merged and both can appear; Claude Code resolves same-name skills by location. Neither protects you from two different names with the same job.

Self-studyHow big can a library get? Contested3 min▶

There is no published threshold for skills, and two kinds of evidence point different ways. Vendors design for large libraries: Anthropic's guide speaks of the assistant choosing "from potentially 100+ available Skills", and Claude Code and Codex both budget the listing (about 1% and 2% of the context window) and shorten or drop descriptions when it overflows. Against that, a 2025 study of a different but related problem, picking one tool from a large catalogue of MCP tools, found selection accuracy of 13.62% with the whole catalogue in the prompt and 43.13% when a retrieval step narrowed it first (Gan and Sun, RAG-MCP). That is tools, not skills, on a stress benchmark. What both sides agree on: the more candidates and the more alike they are, the more the descriptions have to carry.

Real world

When the listing overflows. Claude Code's docs describe what happens when a library outgrows its budget: it keeps every skill name but drops descriptions, starting with the skills you invoke least, "which removes the keywords Claude needs to match your request". A long, stuffed description does not only misroute on its own; it spends budget that a neighbour's description needed.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · Rung 1 scores 14 of 60 with 42 requests firing no skill. Rung 2 scores 52 with 6 false fires. What changed in kind, not just in number?

Both rungs have 18 skills and the same firing line of 1.20. Specific words let requests find their skills, and also let stray words in requests find skills they should not.

2 · Keyword stuffing takes "no skill fired" from 1 to 0. Why does the bench still call it a trap?

Count all four outcomes, not one. A move that fixes one miss by creating three wrong fires is a loss, and it costs context too.

3 · After adding sector-scan, a copy of market-scan with one sentence edited, what does the bench report?

Requests meant for market-scan now split between the twins. Same job, two names: the assistant has to guess, and the guess is decided by small word differences and list order.
