Upkeep: overlap, drift, token cost, retirement

A library that routed well in March can route badly by June without anyone touching a description. Someone adds a skill that copies a neighbour, someone edits a body and forgets the description, the list of skills grows until the assistant starts cutting it short. Where we start

Sessions 1 to 5 built a library and tested it. This one keeps it working. The question has not changed: for each request you send, does it reach the right skill, and what does keeping that true cost? Part 1 · covers overlap audits, merging and splitting

Find the pairs that fight

5 min live

Two skills overlap when a request could reasonably go to either. The router does not see your intentions, only the words in two descriptions, so when those words are mostly the same, the choice between them is decided by small differences in phrasing or by which one is listed first. An overlap audit finds those pairs before your colleagues do: put the descriptions side by side, then send a shared test set through and count which pair collides most.

LiveAn overlap audit2 min▶

Step one, by eye. List every pair of skills whose descriptions share most of their words. Read the pairs side by side, as in the figure. If you cannot say in one sentence which requests belong to which, neither can the router.

Step two, by count. Send one shared test set through the whole library (the session 5 set works) and count misroutes for each pair of "should reach" and "fired". The pair with the highest count is the worst-colliding pair: the two skills that most often take each other's work.

On the bench, someone at Pemberton & Thistle copied market-scan as sector-scan and edited one phrase (constructed). The copy takes requests 5 and 6 from market-scan, wrong-skill outcomes rise from 1 to 3, and the bench names the worst pair: market-scan + sector-scan (2). Request 6 is the uncomfortable one: both scored 1.61, and the copy won only because it sits higher in the list. The bench router is a modelled stand-in (a BM25 keyword scorer); a real assistant reads with a language model, so take the direction, not the numbers.

What the audit showsThe fixOn the bench (constructed)
Two names, one jobMerge: keep the better-named skill, fold in any step the other had, retire the other with a pointer (Part 3)Merging sector-scan back into market-scan returns the library to rung 4: 55 of 60

Both moves make the same promise: one job per skill, one skill per job. Codex's guidance says the same in its own words: one job per skill, with clear scope and boundaries in the description.

Self-studySame names across locations2 min▶

Overlap also happens by name, when the same skill sits in two places. The products handle it differently, as documented on 2026-11-25:

AssistantTwo skills with the same name
Claude CodeOne wins by location: enterprise overrides personal, personal overrides project
OpenAI CodexNot merged; both can appear in the list

So the same accident has two different symptoms. In Claude Code, your project's fix can be silently shadowed by an older personal copy. In Codex, two near-identical entries compete exactly like market-scan and sector-scan above. The audit habit covers both: list every skill the assistant can actually see, not just the folder you are editing.

Real world

The docs expect duplicates. OpenAI's "Build skills" page states plainly that Codex does not merge skills that share a name, so both can appear when the same skill exists in two locations. Its advice for descriptions, clear scope and boundaries with the main use case first, is the preventive half of an overlap audit.

Part 2 · covers description drift and an owner per skill

When the description stops telling the truth

5 min live

The router reads only the description. The work happens in the body. When someone improves the body and leaves the description alone, the two drift apart: requests keep going to a skill that no longer does that job, or keep missing a skill that now does. Nothing breaks loudly. The skill works perfectly when it fires; it just stops firing for the right things.

LiveDrift3 min▶

In the Constructed Pemberton & Thistle example, Priya adds a step to market-scan in April: when a scan names one company, profile it too. Useful. But the description still ends with the line from session 2, quoted from the bench library:

★ market-scan, the line that did not moveDo not use for one named company (competitor-profile) or for academic papers (lit-review).

So a request to profile one company still goes to competitor-profile, and the new step in market-scan only runs when someone happens to mention a company inside a sector scan. Drift has two shapes: a request reaches a skill that no longer does that job (the body dropped it), or a request misses a skill that now does (the body gained it). Either way, the fix is the same habit: every edit to a body ends with re-reading the description, and then re-running the trigger tests from session 5.

LiveAn owner and a review date per skill2 min▶

Drift happens to skills nobody owns. The open specification gives you a place to record who does: the optional metadata field, an arbitrary key-value map. The specification's own example uses author and version; nothing stops you adding the two keys that matter for upkeep.

★ Frontmatter with an owner (constructed Pemberton & Thistle example)--- name: market-scan description: Runs a desk research scan of a market or sector: ... metadata: owner: priya last-reviewed: "2027-01-12" version: "1.3" ---

The owner re-reads the description after every body edit and answers for the skill at the quarterly review. A skill with no owner at the review is a retirement candidate by default. The dates and version above are constructed; your keys can be any you will actually maintain.

Self-studySecurity review on every update3 min▶

Upkeep is also a security habit. Anthropic's Agent Skills overview advises using skills only from trusted sources and auditing every bundled file, not just SKILL.md: scripts, references and assets. It singles out skills that fetch data from external URLs as risky, because what they fetch can carry instructions, and notes that even a trustworthy skill can be compromised if its external dependencies change.

The practical rule for a library: a review is not done once. Any update to a skill you did not write, and any change in what a skill fetches, gets the same audit as the first install. Put the date of the last audit next to the owner.

Real world

Trusted today is not trusted forever. Anthropic's security considerations for Agent Skills warn that a malicious skill can direct tool use or run code that does not match its stated purpose, and that a skill pulling from external sources can change behaviour without its own files changing. That is drift with consequences: the description says one thing, the behaviour does another, and only a review catches it.

Part 3 · covers context cost and retirement

What the library costs, and how to retire a skill

5 min live

Every installed skill pays rent. Its name and description sit in the assistant's context in every session, whether or not it ever fires. A library is cheap at five skills and noticeably expensive at fifty, and both Claude Code and Codex respond to the expense the same way: when the list outgrows its budget, descriptions get shortened or dropped. The cheapest skill to keep is the one you retire on purpose.

LiveThe standing cost3 min▶

Anthropic's overview puts Level 1, the name and description, at about 100 tokens per skill, always loaded. The two coding assistants cap the total and say what happens when you exceed it:

AssistantListing budgetWhen it overflows
Claude CodeAbout 1% of the model's context window; each description plus its when-to-use text is cut at 1,536 characters in the listingDescriptions are dropped, starting with the least-invoked skills; /doctor estimates what the listing costs
OpenAI CodexAt most 2% of the context window, or 8,000 characters when the window size is unknown; skills.max_context_tokens raises it up to 10,000 tokensDescriptions are shortened first; some skills may be left out, with a warning

On the bench (constructed), the rung 4 library loads 5,391 characters of description; adding the near-duplicate raises it to 5,685; stuffing every description raises it to 6,900. Note what the drop rule means for upkeep: a skill that rarely fires is the first to lose its description in Claude Code, so a large library can make your rarely used skills invisible without telling you.

LiveRetire with a pointer2 min▶

Deleting a skill is fast and leaves people stuck: a colleague types the old name, nothing happens, nobody knows where the job went. Retire in three moves instead.

  1. Disable first. Stop the assistant choosing it while the files still exist. Claude Code: disable-model-invocation: true in the frontmatter (only a person can invoke it). Codex: a [[skills.config]] entry with enabled = false.
  2. Leave a tombstone. A short note at the old location saying where the job went, when, and why.
  3. Delete after one review cycle, once nobody has reached for it.
★ newsletter/RETIRED.md (constructed Pemberton & Thistle example)Retired 2027-01-12 by priya. The monthly newsletter is now a template, not a skill: the section order never changed and no run needed judgment. Use: templates/newsletter.docx Disabled since the Q1 review; delete at the Q2 review if unused.
Self-studyHow many skills is too many? Contested3 min▶

One side. The vendors design for large libraries. Anthropic's best practices describe the description being used to choose the right skill "from potentially 100+ available Skills", and both Claude Code and Codex manage growth with a budget rather than a limit on count.

The other side. Gan and Sun's RAG-MCP paper (arXiv 2505.03275, May 2025; abstract read at source) put a large catalogue of MCP tools into the prompt and measured tool selection accuracy at 13.62%; retrieving a relevant subset first raised it to 43.13% and cut prompt tokens by over half. That is MCP tools on a stress benchmark, not skills, and its setup is not a skills library.

What nobody has published is a threshold for skills. Treat any number you see quoted as a claim to check. What you can measure is your own library: run the audit each quarter and watch whether the held-out score falls as the count rises.

Real world

"Skill descriptions are cut short." The Claude Code skills docs carry a troubleshooting section for exactly this: when many skills are installed, the listing budget of about 1% of the context window overflows and descriptions are dropped, least-invoked first, and /doctor shows the estimate. Codex documents the parallel case: put the main use case and trigger words first, so matching survives when descriptions are shortened.

Build-along

The quarterly library review

★ 22 min · everyone builds

It is Pemberton & Thistle's first quarterly review (constructed). Since session 5 someone added sector-scan, and a colleague has proposed bolting extra keywords onto every description "so nothing gets missed". You will score the library as found, test the proposal, fix the overlap, quote the honest number and write it all down. Score before you argue. Every decision in the log above carries a before and an after. The stuffing proposal sounded reasonable until it had numbers next to it. A library review without a test set is a meeting about opinions; with one, it is twenty minutes and a log entry.

Homework

After the last session

30 min
  1. Run your own overlap audit. List every skill your assistant can actually see, in every location, and read the pairs whose descriptions share most of their words. Send your session 5 test set through and name your worst-colliding pair.
  2. Write your first upkeep log entry. Date, change, reason, owner, the numbers before and after, and any pointer left behind. One entry is enough to start the habit.
  3. Set an owner and a last-reviewed date for every skill, in the metadata field or in a library index. Any skill nobody claims goes on the retirement list.
  4. Retire one skill with a pointer. Disable it first, leave a tombstone saying where the job went and when, and put the delete date on your next review.
Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · The bench reports "Worst-colliding pair: market-scan + sector-scan (2)". What does that tell you?

The pair count is misroutes between the "should reach" skill and the one that fired. The highest count marks the overlap to fix first, usually by merging or by sharpening one description.

2 · Why disable a skill and leave a tombstone, rather than delete it straight away?

Silent disappearance leaves people typing a name that does nothing. A pointer turns a dead end into a redirect, and the review cycle catches anything that still depended on the old skill.

3 · Why does keyword-stuffing every description raise the library's standing cost?

Level 1 is always loaded. Longer descriptions also hit the listing budgets sooner, at which point Claude Code drops and Codex shortens descriptions.
