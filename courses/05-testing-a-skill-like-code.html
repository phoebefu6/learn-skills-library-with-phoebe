Part 0

Where we start

A skill has two ways to fail. It can fail to load, or load for the wrong request: that is a trigger failure, and the description is where you fix it. Or it can load and then write something wrong: that is an output failure, and the body is where you fix it. Both are testable with the same discipline as code: write the cases down before you edit, run all of them, and keep the ones that matter forever. Our running case is the Constructed Pemberton & Thistle example, an invented four-person consultancy, and tonight its meeting-minutes skill gets a test suite.

Part 1 · covers trigger tests

Should fire, should not fire

5 min live

A trigger test is a request plus one expected answer: this skill fires, or it does not. The open format's guide on optimizing descriptions asks for about 20 such queries, 8 to 10 of each kind, and says the most valuable negatives are near-misses: requests that share the skill's words but need something else. Below is the Constructed Pemberton & Thistle example, 12 cases for meeting-minutes, each routed by the bench's stand-in router.

LiveTwo kinds of trigger test2 min▶

Should-trigger cases check that the skill is found when it is needed. Vary them the way real people vary: the guide asks for different phrasing, more and less explicit requests, more and less detail, and simple against complex asks. "Minutes please" and a long paragraph of context about the Norbury board are both real requests for the same skill.

Should-not-trigger cases check that the skill stays quiet when another skill, or no skill, owns the request. A test set with only positives is like a smoke detector you only ever test with smoke: it tells you nothing about false alarms.

The open format's guide suggests about 20 queries, 8 to 10 of each kind. Codex's skills guide gives the same advice in one line: test prompts against the description. We use 12 tonight so every case fits on one screen.

LiveNear-misses are the valuable negatives2 min▶

A near-miss shares the skill's vocabulary but needs a different job done. For meeting-minutes, that is interview transcripts (a neighbour's job), workshop preparation (another neighbour), or booking a meeting room (no skill at all). These are the requests a description can genuinely confuse.

A weak negative shares nothing: "summarise this article about AI in local government" scored 0.00 for every skill in the figure. It passes, and it will pass after any edit you make to meeting-minutes, which means it cannot tell you anything. Spend your negative slots on requests that could plausibly go wrong.

Self-studyRuns per query and trigger rate3 min▶

A language model is nondeterministic: the same request can load a skill on one run and not the next. The open format's guide therefore runs each query several times, three to start, and records a trigger rate: the share of runs in which the skill fired. A should-trigger case passes if its rate is above a threshold (the guide uses 0.5), and a should-not-trigger case passes if its rate is below it.

The bench router is a modelled stand-in, BM25 keyword scoring, not a language model. It is deterministic, so one run per request is enough on the bench. A real assistant needs the repeats, and a case sitting near the threshold (like the 1.18 against a 1.20 line above) is exactly the case whose rate will wobble between runs.

Real world

Weak and strong negatives. The open format's guide on optimizing descriptions works its advice through a CSV-analysis skill and makes the same distinction: a negative that obviously has nothing to do with the skill tests nothing, while one that shares its keywords but needs something else is where the description earns its keep. The guide's own phrase for the useful kind is near-misses, and it calls them the most valuable negatives in the set.

Part 2 · covers held-out sets and golden outputs

Tune on some, check on the rest

5 min live

Two separate questions need two separate kinds of evidence. Does the description route well on requests you have not seen? For that, hold some requests back and never tune on them. Does the skill, once loaded, write what it should? For that, keep a few golden cases with assertions that read the output. The Constructed Pemberton & Thistle example below grades one golden case twice: with the skill, and without it.

LiveTrain and validation3 min▶

Every time you edit a description to fix a failing request, you fit the description to that request. Do it often enough and the description passes your whole test set while doing no better on requests you have never seen. That is overfitting, and code testers know it as "teaching to the test".

The open format's guide splits trigger queries into a train set of about 60% that you tune on and a validation set of about 40% that you only check, keeps the split fixed across iterations, and picks the best description by validation pass rate, not train pass rate. It also warns against adding specific keywords lifted from failed queries, since that is the fastest way to overfit, and notes that about five iterations is usually enough.

The bench in session 4 did exactly this: 40 tuning requests, 20 held out. Pemberton & Thistle's rung 4 library (constructed) scored 37 of 40 on tuning and 18 of 20 on the held-out set. The held-out number is the one to quote.

LiveGolden outputs and assertions2 min▶

The open format's guide on evaluating output quality defines a test case as a prompt, an expected output and, optionally, input files, kept in evals/evals.json. Start with two or three cases. Run each one with the skill and without it (or against the previous version), because a skill only earns its description if the output is better with it.

Assertions come after the first run, once you have seen what the outputs actually look like. Good assertions are verifiable ("every action has an owner and a date"), not vague ("the minutes are good") and not brittle ("the third line says Priya"). Grading needs concrete evidence: the count, the quote, the missing heading.

The guide frames the result as a benchmark delta: what the skill costs (time, tokens) against what it buys (pass rate). General evaluation methods, graders and rubrics are taught in Learn AI Evals.

Self-studyAnthropic: build evaluations first3 min▶

Anthropic's skill authoring best practices put evaluations before documentation: "Build three scenarios" that show where the assistant fails without the skill, and the authoring checklist asks for "At least three evaluations created". The same page advises testing with Haiku, Sonnet and Opus, since what is enough guidance for one model may be too little or too much for another.

That page also says there is not currently a built-in way to run these evaluations. The Claude Code skills docs have since described a skill-creator plugin that tunes descriptions with should-trigger and should-not-trigger prompts, runs blind A/B comparisons between versions and benchmarks a skill with and without it, and they describe evals for plugins too. Tooling moves fast here; the habit (cases first, baseline second, edit third) does not.

Real world

Delete the assertions that cannot fail. The open format's evaluation guide is blunt about it: "Remove or replace assertions that always pass in both configurations." An assertion that passes with the skill and without it, like the Norbury Council check in the figure, makes the pass rate look healthy while measuring nothing the skill contributes.

Part 3 · covers regression after an edit and testing against the passing state

Re-run everything after every edit

5 min live

In a library, every description competes with every other one, so an edit to one skill moves the odds for every request. The fix you aimed at is rarely the only thing that changes. The figure is real bench output on the Constructed Pemberton & Thistle library, going from rung 2 to rung 3 of session 4's ladder.

LiveRegression: the row nobody touched3 min▶

On rung 3 of the bench, Pemberton & Thistle (constructed) added a "Do not use for" line to every description to stop six false fires. Overall, false fires fell from 6 to 3. But request #53, "what's the time in Singapore right now?", which had correctly fired nothing (top score 1.19, just under the line), started firing newsletter at 1.23. The newsletter's new line is about client emails and has nothing to do with time; the request flipped because the newsletter description says "when it is time to write", and every score in the library moved when the descriptions grew.

The lesson carries straight over to a real assistant, where the router is a language model and the coupling is harder to see, not easier: re-run the whole set after every edit, not just the cases you meant to fix. The cases you did not think about are the ones regression tests exist for.

LiveTest the test against the passing state2 min▶

A test that can never pass, or can never fail, looks exactly like a test that is working. The weak negative in Part 1 is one example: it passes whatever you do to the description. The always-passing assertion in Part 2 is another.

So check every test against a known state. Each case should pass on a description you know is good and fail on one you know is bad. The bench engine's own self-test does this: one property, that each skill's own "what" text routes to itself, holds on the real router; with a planted fault (the router picks the lowest score instead of the highest) the same property breaks on all 19 skills. If the planted fault had left it passing, the self-test would have been measuring nothing.

Self-studyVersion comparison2 min▶

The open format's evaluation guide lets the baseline be the previous version of the skill instead of no skill at all. That turns every edit into a comparison: same cases, old version against new. To make that possible, snapshot the skill folder before you edit (a copy, or a commit if it lives in version control), and keep the test cases next to it so they travel together.

The Claude Code docs describe the skill-creator plugin running blind A/B comparisons between two versions. Whatever the tooling, the discipline is the one software teams use: never ship an edit you have not compared against the version it replaces.

Real world

When a skill triggers too often. Claude Code's troubleshooting for an over-eager skill says to make the description more specific, or to set disable-model-invocation: true so only you can call it. Making it more specific is an edit, and every edit is a reason to re-run the full set: a sharper description for one skill changes the competition for all of them.

A 12-case trigger test set

We write a test set for Pemberton & Thistle's meeting-minutes skill (Constructed Pemberton & Thistle example) on the bench's "split" rung, where it became its own skill. Six requests should fire it and six near-misses should not. None of them is from session 4's sixty; they are new. Copy the description under test. This is the meeting-minutes description on the "split" rung of the bench, verbatim: the "what + when" text followed by its "Do not use for" line. A test set always belongs to one exact version of the text.

★ Step 1 · meeting-minutes, as the bench has it (constructed)Turns a meeting recording or rough notes into minutes: attendees, decisions, action items with owners and dates. Use when someone shares a call recording or meeting notes and asks for minutes or actions. Do not use for research transcripts, themes or quotes (interview-synthesis).

Write six should-fire cases. Vary them on purpose: a direct ask, one that lists the outputs, an indirect one that never says "minutes", a terse one, a long one with real context, and a paraphrase. Type each one into the try widget below and watch which skill fires; then type your own.

Write six should-not-fire near-misses. Pick requests a neighbour owns or that share the skill's words: interview transcripts (interview-synthesis), workshop preparation (workshop-pack), booking a meeting room, summarising an article, an executive summary of a report, survey responses. A should-not-fire case passes when meeting-minutes stays quiet, whether a neighbour fires or nothing does.

Run every case and write down what the router printed. We ran each request with the bench's command-line twin on the split rung; these are its outputs, not estimates.

Read every failure and decide who is wrong: the test or the description. Three cases failed, and each needs a different answer.

★ Step 5 · the three failures, read one by one#3 "what did we decide ... who owns each next step?" none, top 1.18 The test is right: people really ask this way. The description says "decisions" and "owners"; the request says "decide" and "owns", and this keyword router does not match them. Do NOT paste "decide" and "next step" into the description: that overfits to one failed query. Describe the intent in general terms instead, then check the held-out cases. A language model would likely bridge these words; the bench cannot, so treat this as a direction, not a forecast. #4 "minutes please" none, top 1.09 Probably the test is wrong. Two words with nothing attached give any router too little to go on, and the open format's guide notes agents often skip skills for simple one-step requests. Rewrite the case with the material a real request carries, or keep it as an explicit-call case: someone who wants exactly this types /meeting-minutes. #9 "book a meeting room for the client call on Friday" meeting-minutes 2.27 The description is wrong. It shares "meeting" and "call" with the request. Session 4's "book a meeting room for Thursday at 2" scores only 1.09 here; adding "client call" pushed it over the line. Fix: add specificity about what the skill does not do, e.g. "Do not use for booking rooms or scheduling meetings." Then re-run all 12, not just #9 (Part 3). Also note #10 passed at 0.00 for every skill: a weak negative. Swap it for a request that shares the skill's words. And #6 passed with slide-polish only 0.43 behind ("tidy"): a narrow margin to watch after every edit.

Add three golden-output assertions. Trigger tests say the skill loaded; these say it did the job. Write them after a first run, as verifiable checks with evidence. The case and assertions below are constructed and have not been run.

★ Step 6 · one golden case, three assertions (constructed, not run)CASE prompt: "write up the Norbury board notes as minutes" files: board-notes.txt (6 attendees, 2 decisions, 3 actions) expected: minutes with Attendees, Decisions and Actions ASSERT 1 Every action item names one owner and one date. evidence: count action lines missing either (expect 0) ASSERT 2 Both decisions in the notes appear under a Decisions heading. evidence: quote each decision and the heading it sits under ASSERT 3 The attendee list matches the 6 names in the notes; none added. evidence: list any name present in one but not the other RUN with the skill, and without it, as the baseline. DROP any assertion that passes in both runs.

Save it as the regression suite. Keep the 12 cases and the golden case in the skill's folder, with the split fixed (for example, cases 1 to 8 for tuning and 9 to 12 held out), and the date of the description they were run against. From now on, every edit to any skill in the library is followed by a full run of every suite.

A failing test is information, not a verdict. Before you change a description, ask whether the test describes a request a real person would send. If not, fix the test. If so, fix the description in general terms, then re-run everything. The two failures you get wrong are fixing a test that was right, and stuffing a description to pass one case.

Homework

Before session 6

30 min
  1. Write a 12-case trigger set for one skill you own. Six should fire, varied in phrasing, explicitness and detail; six near-misses taken from the jobs of its closest neighbours. Strike any negative that shares no words with the skill.
  2. Run every case three times in your real assistant and record the trigger rate for each. Mark the cases whose rate changes between runs: they sit close to the line and will move first after an edit.
  3. Fix a split and keep it. Choose which cases you tune on and which you only check, write it down, and report the held-out pass rate when you tell anyone how good the skill is.
  4. Write two or three golden cases with assertions, run each with and without the skill, and delete any assertion that passes in both runs. Then make one small edit to the description and re-run everything.
Check yourself

Three questions

Clear all three and session 5 gets stamped in your passport.

1 · You have one slot left for a should-not-fire case for meeting-minutes. Which request tells you the most?

A near-miss shares the skill's words but needs something else. On the bench this one fired meeting-minutes at 2.27 and exposed a real fault; the article request scored 0.00 for every skill and could never fail.

2 · Why keep some requests held out instead of tuning the description on all of them?

Tuning fits the description to what you can see. The bench's rung 4 library scored 37 of 40 on tuning and 18 of 20 held out; the held-out number is the honest one to quote.

3 · Why check each test against a known-good and a known-bad version before trusting it?

The bench's self-test holds on the real router and breaks on all 19 skills when a fault is planted (lowest score instead of highest). A check that survived the planted fault would have been measuring nothing.
